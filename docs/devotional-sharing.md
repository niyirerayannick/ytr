# Devotional sharing & repost images

Each published devotion now has a stable public URL (`/devotions/<slug>/`)
with a "Share Devotion" button that opens a share sheet: direct links to
WhatsApp, Facebook, X, Telegram, and email, a copy-link action, the browser's
native share sheet where available, and a "Create Repost" flow that generates
a branded, bilingual YTR devotional image.

## Architecture: server-side rendering, not `<canvas>`

The devotion list page used to have a "Download to repost" button that drew
an image client-side with `<canvas>`, for the featured "today" devotion only,
in English only, with no branding footer. That's been replaced.

The repost image is now rendered **server-side** with Pillow
(`apps/devotions/share_cards.py`), for two reasons:

- **It has to double as the `og:image`.** Link previews are generated by
  Facebook's/WhatsApp's/X's crawlers, which never execute JavaScript — a
  `<canvas>` export doesn't exist for them. The og:image has to be a real,
  fetchable URL.
- **Predictable typography.** Pillow renders the same bytes for every
  visitor, instead of depending on whatever fonts and canvas quirks a given
  phone's browser has.

Pillow was already a dependency (used for admin image uploads), so this adds
no new packages. Two bundled variable fonts back it: `static/fonts/WorkSans-Variable.ttf`
and `-Italic-Variable.ttf` (Work Sans, SIL Open Font License, same family the
site already uses via Google Fonts for its `sans` typeface) — bundled locally
because Pillow needs a real font file on disk, not a CDN link.

The client only ever *fetches* the rendered PNG (as a blob, to preview/share/save
it) or *links* to it (`og:image`); no image generation happens in the browser.

## URLs

- `GET /devotions/<slug>/` — the devotion detail/share page. Published only;
  draft/pending/rejected devotions 404, including for a logged-in non-admin
  guessing a slug.
- `GET /devotions/<slug>/share-image.png?lang=<en|rw>&format=square` — the
  repost PNG. `lang` and `format` are validated against small allow-lists
  (`apps/devotions/share_cards.py: LANGUAGES`, `FORMATS`); anything else is a
  400, not a 500 or a silently-ignored default. Only a `published` devotion
  can generate one (404 otherwise), and a language with no authored content
  for that devotion is a 400 — never a blank or auto-translated image.

## Bilingual behavior

The site's EN/KN toggle is instant and client-side (a `body` class flipped
by `site.js`, persisted in `localStorage`) — the server never knows which
language a given request is "in". So:

- The share-sheet links (WhatsApp text, X text, email subject/body, etc.) are
  built in JS (`static/js/devotion-share.js`) at the moment "Share" is
  clicked, reading the same `lang-rw` body class the rest of the site uses,
  from a small JSON payload the detail page embeds via Django's `json_script`
  filter (`#devotionShareData`) — both languages' copy ships in the page
  once; JS just picks.
- The repost language selector defaults to the current site language, but the
  visitor can change it before generating the image. Devotion content is
  never machine-translated: `Devotion.has_language(lang)` checks that both
  the verse text and reflection are actually authored in that language, and
  a language that isn't disables its button with a "Kinyarwanda version
  unavailable" note instead of silently falling back to English text under a
  Kinyarwanda label. `Devotion.share_excerpt(lang)` only ever reads that
  language's own field.

## Card content and contact details

The card shows the devotion's `verse_ref` as the heading (the model has no
separate "title" field — `verse_ref` is what's authored and displayed
everywhere else too), a short excerpt of the reflection (word-wrapped, capped
at ~45 words with an ellipsis rather than shrinking text past readability),
and a footer with the YTR brand mark plus a "Read today's devotion…" CTA.

Contact lines (website, email, phone) come from `SiteSettings` — the same
singleton that already backs the site footer and contact page —
`website_url` was added as a new field (nothing else fit; email/phone already
existed). `share_cards.footer_lines()` only emits a line for a field that's
actually configured; an unset field is omitted, never replaced with a
placeholder. See `apps/devotions/tests.py: ShareCardFooterLinesTests`.

## Caching

Rendering is deterministic: the same devotion content, language, format, and
`SiteSettings` state always produce the same PNG. `share_cards.cache_key()`
hashes `(devotion.pk, lang, format, devotion.updated_at, site_settings.updated_at)`
and the view stores the rendered bytes in Django's cache (`django.core.cache.cache`,
indefinite timeout) under that key — editing the devotion or the contact
details changes the key, so the next request re-renders automatically; there
is no separate invalidation step to remember. The response also sets
`Cache-Control: public, max-age=86400` and an `ETag` so browsers/CDNs cache it
too.

## Formats

Only `square` (1080×1080) ships. A `story`/status format (1080×1920) was
scoped out for this pass to keep the renderer's first version simple — the
layout math in `share_cards.render_devotion_card()` is written to be
extended with a second entry in `FORMATS` later rather than rewritten.

## Security

- `lang`/`format` are strict allow-lists, never interpolated into a path or
  template name.
- Only `status=published` devotions are ever reachable via the detail page
  or the share-image endpoint — same rule the rest of the public site
  already enforces for articles/episodes/videos.
- The image renderer only reads devotion fields and `SiteSettings`; nothing
  from the request (headers, query params beyond the two validated ones)
  reaches the renderer or gets drawn onto the image.

## What's deferred

- **Story/status format (1080×1920).** Square covers WhatsApp Status,
  Instagram, Facebook, X, and Telegram well enough for a first release.
- **Share-action analytics** (counting WhatsApp/Facebook/etc. clicks). Would
  need a new model and is easy to bolt on later; left out to avoid scope
  creep on this pass. Note that even if added, it could only count that a
  visitor *clicked* "Share on X", never confirm they completed posting.
- **Automated browser tests for the share dialog.** Covered manually
  end-to-end (dialog open/close, Escape-to-close, all six platform links'
  encoding, repost generation in both languages, mobile + desktop layout) —
  see the PR description for what was checked. The repo's existing Playwright
  suite (`e2e/`) is scoped to PWA install/offline/service-worker behavior;
  adding a dedicated share-dialog spec there is a reasonable follow-up rather
  than part of this change.
